The problem

A signature proves a document wasn't edited. It cannot prove the record is complete.

SIH26149 asks for secure data erasure and advanced file recovery with verifiable proof. Tools for both already exist and are good at their jobs. The gap is not erasure and it is not recovery, it is what happens to the record afterwards.

BitRaser, Blancco, EnCase and FTK all sign each certificate independently. That signature is real and it works: it proves that one document has not been altered. But nothing binds certificate #5 to certificate #4. Delete one from the middle of a case file and every surviving certificate still verifies perfectly. The tampering leaves no trace, because there is nothing for it to leave a trace in.

Under BSA 2023 §63(4), in force since July 2024, electronic evidence needs a certificate signed by both the person in charge and an expert. The statute changed; the tools did not.

The mechanism

Chain the operations, and removal stops being invisible

Architecture

Two machines, two keys, one record

The second signature is the part that cannot be faked by whoever is running the tool, because the key that makes it lives on a different computer. Both laptops sit on one hotspot; the operator sends an entry hash, the witness signs it with its own key and keeps its own copy.

Why this is the hard part to copy

Any team can hash a file. The difficulty is making the tool refuse when the second party is missing, rather than quietly recording a weaker result, and doing that check before the destructive step, not after. That behaviour is the product.

What gets signed

Sixteen fields, length-prefixed, then hashed

Fields are never joined with a separator. Each is prefixed with its own length before hashing, so no two different records can produce the same signing bytes. A pipe-joined encoding in the predecessor codebase allowed exactly that collision; there is now a regression test that must never be deleted.

The honest bound on the custody claim

The tier reached on real hardware is WITNESS_COSIGNED, not FULL_CUSTODY. Full custody additionally requires a confirmed presence device, which is designed and not shipped. The tool refuses to print the higher label, and so do we.

The moment that lands

Row 2 is an operation that did not happen, permanently recorded. Ask any competing tool to show you the log entry for an operation it refused to perform. There isn't one , a blocked attempt simply leaves no trace.

Self-correction

A bug we found in our own tool, hours before the deadline

Building the demo dataset, recovery came back 2 of 4 byte-identical rather than 4 of 4. The carved ZIP would not open at all, and the tool still reported truncated = false.

The cause: the carver treated a footer marker as the end of the file. In a ZIP, PK\x05\x06 is only four bytes but it opens a 22-byte End of Central Directory record, so 18 bytes were cut, producing an archive no reader will open.

620 tests passed anyway, because the byte-identical test covered JPEG, PNG and BMP: exactly the three formats whose footer marker is the last byte of the file.

What we fixed

The carver resolves the true trailer length, and when a trailer genuinely is cut off it now reports truncated = true instead of claiming completeness. Ten new tests cover both halves.

Why we are telling you

Reporting a corrupt file as complete is precisely the overclaim this project exists to prevent. A team that hides that has learned nothing from building it. 4/4 now, and the ZIP opens.

Scale & economics

Why this is a product, not a project

The demand is regulatory, not discretionary

DPDP Act §8(7) requires erasure. BSA 2023 §63(4) requires the two-party certificate. CERT-In, RBI and SEBI all impose retention and disposal duties. Organisations do not choose whether to comply.

≈ $650M serviceable slice (non-mobile), growing at ~40% CAGR per Deloitte, DSCI. Cited from the published figures, not modelled by us.

Why incumbents cannot simply add this

  • Blancco and BitRaser are STQC-certified. Changing certificate structure means recertification, a multi-year cost, which is exactly why a certified vendor moves slowly.
  • EnCase and FTK are foreign products. Building a certificate native to one country's evidence statute is poor economics for them, and carries export-control exposure.
  • None of them cross the erasure/recovery boundary. The two functions live in separate product lines with separate buyers.
  • The conjunction is the moat, erasure and recovery in one ledger, dual-signed, statute-native, post-quantum. Each piece exists somewhere; the combination does not.

Stated plainly

We are pre-revenue and pre-certification. The honest description is a working prototype with a named wedge, the BSA §63(4) certificate no tool emits natively, and a costed path to a first lab and STQC certification. Not a company yet.

The verification is implemented three times on purpose

Python, JavaScript and Rust. Two implementations by one author can share a misreading of the spec and agree while both are wrong. A third, in a language with different string and integer semantics, catches that class of error. A test asserts all three produce identical entry hashes and identical verdicts, it is the canary, and it must never be marked xfail.
