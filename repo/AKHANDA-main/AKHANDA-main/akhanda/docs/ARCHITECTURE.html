A forensic erasure and recovery tool where every operation is recorded in a dual-signed, witness-anchored ledger. The engineering problem is not cryptography, it is refusing to claim more than was actually achieved, and making that refusal mechanical rather than a habit.

01 The core idea

One sentence, then the machinery that makes it true.

Existing tools sign each certificate independently. That proves one document was not edited. It does not prove the sequence is complete, nothing stops a record being removed from the middle of a pile of individually valid PDFs, and every remaining signature still checks out.

Akhanda chains operations into one append-only ledger, requires two independent parties to sign the same record, holds the second key in a separate security domain, and anchors the chain to a witness outside the operator's control.

Four mechanisms carry that claim, and each one exists because a specific attack defeats the mechanism below it:

  • Length-prefixed injective encoding, two different records can never produce identical signing bytes, so one signature can never validate two documents.
  • Hash chaining with prev_hash, an edit, a reorder, or a deletion from the middle breaks the link and names the sequence number.
  • Dual signature over the same entry hash, the operator alone cannot produce a complete record, which is also the shape BSA §63(4) asks for.
  • An independent witness head record, the operator can rebuild the entire chain from entry zero and re-sign it flawlessly; the witness still disagrees.
  • A signed outcome field, an operation that completed but failed its own verification cannot look like a clean one, because how well it went is inside the signature rather than beside it.

03 Trust boundaries

The whole design is one question: which machine can forge which claim? Everything else follows from the answer.

Say the threat model out loud. This defends against an operator who alters the record after the fact, and against a remote attacker who compromises one domain. It does not defend against an insider who controls both domains at the moment of writing. Separation is only as real as the administrative boundary between the two, which is a deployment property, not a code property.

04 Operation lifecycle

This is a genuine ordered sequence, and the order is the security property, which is why these steps are numbered and nothing else on this page is.

  1. Preflight, the fail-closed gate Cheap probes: does the co-signer answer its head endpoint, does the presence device enumerate? No button press is consumed here. If a component you asked for is silent, stop now.
  2. Refusal is recorded, not swallowed A blocked attempt is appended as a REFUSED / NotPerformed entry with its own persisted record. Unplugging the co-signer now logs the attempt instead of hiding it. Exit code 3.
  3. The operation runs, point of no return Overwrite and read-back sampling, or a signature carve. For an erase, nothing after this line can undo what just happened.
  4. Result record is built Every sampled offset, both digests per sample, the honest method_used, the verified flag, the media note. This is the document, not a summary of it.
  5. Presence is requested A human presses a physical control on a separate device. Absence at this point lowers the tier; it never fabricates one.
  6. Entry is built and operator-signed 15 length-prefixed fields behind a domain tag, SHA-256, Ed25519. The tier, the presence reference, and the outcome are all inside the preimage, so none of them can be attached or upgraded afterwards.
  7. Co-signature over the same hash The witness signs the identical entry_hash and extends its own independent head record. Both come back and are attached.
  8. Degradation check If preflight passed but a component died mid-operation, the entry is recorded at the tier actually reached and flagged DEGRADED. This is the residual window, and it is announced rather than hidden.
  9. Record then chain, in that order The result file is written before the chain is saved. A crash between them leaves an orphan record, harmless. The reverse order would leave an entry pointing at evidence that was never written.

Why the preflight has to be first. An erase is irreversible. Checking whether you were permitted to do it after doing it is not a check. The window between step 1 and step 7 cannot be eliminated by any tool that destroys data, it is narrowed to a single operation, and step 8 states its size instead of implying it is closed.

05 Custody tiers

The ladder is additive: each rung is the one below it plus one independent party. A tier is computed from what actually answered, never from what was intended.

All four fields that carry this, custody_tier, presence_ref, operator_key_id, and method, sit inside the signed preimage. Editing any of them on a stored entry breaks its hash, which is asserted directly in tests/test_custody.py.

06 Fail-closed policy

The single most consequential behaviour in the tool, and the one that recently changed.

BEFOREsilent downgrade removed

Co-signer unreachable → record a weaker tier, carry on, exit 0.

An operator who wanted an operation off the record unplugged the co-signer. The tool downgraded itself without complaint and the label went into a ledger nobody reads before the fact. One-second trigger, no trace.

NOWasking makes it required built

Co-signer unreachable → block before the operation, append a REFUSED entry, exit 3.

Opting out explicitly (--no-witness) still degrades cleanly and records the honest tier. --allow-degraded is the deliberate escape hatch. There is no path where a requested component vanishes and the tool proceeds quietly.

The three properties, each separately tested

PropertyWhat it meansHow it is proven
BlockedThe operation does not run. exit code 3, "preflight: BLOCKED"
RecordedThe blocked attempt is in the chain. op_type REFUSED, method NotPerformed
UntouchedThe target is byte-identical afterwards. target.read_bytes() == original

The residual window is real and stated. Preflight confirms every required component is answering before an irreversible operation begins. It cannot cover a component that dies during the operation itself, by then the data is gone. That case is recorded at the tier actually reached and flagged DEGRADED. Every tool that performs an irreversible action has this window; this one narrows it to a single operation and reports its size rather than implying it is closed.

07 The signed outcome

The fifteenth field, and the one that took a format break to add. It answers the question a forensics judge asks second.

The defect it closes. An erase whose read-back sampling failed used to produce a ledger entry indistinguishable from a clean one. cli show printed the same ERASE / Clear line either way, and the certificate summarised it as a success. The verified flag lived only in the result record — hash-committed and therefore tamper-evident, but not in the entry, and the entry is what a human reads and a certificate quotes.

A tool whose entire pitch is that it refuses to overclaim was quietly overclaiming in its own ledger.

ValueMeansProduced by
VERIFIEDCompleted, and its own verification passed. read-back sampling matched the written pattern
UNVERIFIEDCompleted, but the check did not pass. sampling mismatch, or a filesystem that could not be identified
PARTIALCompleted with known incompleteness. a carve with a guessed end boundary; a copy-on-write filesystem
NOT_PERFORMEDNothing ran. a REFUSED entry from the fail-closed preflight

Why it cost a format break, and why that was the moment to take it

Adding a field to HASHED_FIELDS changes the signing preimage, so every chain written under the old format stops verifying. That is correct and intended — a migration that rewrites signed entries is precisely the thing this tool exists to detect. The window for a free break closes the moment a chain leaves the building, and it had not yet.

The field list is read by five places, and changing it in four is a silent break:

The verifier also refuses a chain written under a different ENTRY_VERSION rather than checking it against the wrong field list. Mis-verifying quietly is worse than stopping.

08 Three verifiers, one contract

The verification path is written three times, in three languages, on purpose.

Two implementations written by the same author can share a misreading of the specification — they agree, and they are both wrong together. A third, in a language with different string, integer, and byte semantics, is the cheapest way to catch that class of error. It is also the only test here that would fail if the specification were wrong rather than the code.

ImplementationLOCRunsVerifies
src/attestation/core.py408 the tool itselfstructure + operator + concurring signatures
console/index.html344 the viewer's browserstructure only — and says so on the page
rust/akhanda-verify568 a standalone binarystructure + both signature layers

Why the third one is Rust

  • Memory safety is compiler-enforced, not asserted. #![forbid(unsafe_code)] sits on both crate roots — production code containing unsafe does not build. For a forensic tool the verifier is the component a third party runs on evidence they did not produce.
  • No dependency on this project at runtime. One binary, one JSON file, one public key. No network, no configuration, no environment. A verifier that needs a server stops working when the server does, and the point is that someone can check the evidence years later.
  • Different semantics catch different bugs. Rust's explicit integer widths and byte-level string handling make a length-prefix mistake fail loudly where a dynamically typed language can paper over it.
  • The exit code is the interface. 0 verified, 1 broken, 2 usage — usable directly in a script or in CI.

Honest scope. Rust is used for the verifier and nothing else. The erase and recovery paths stay in Python, where they call platform tools and are easier for the team to read and defend. Adding Rust where it does not earn its place would be scope, not security. cargo test and cargo clippy -- -D warnings both run clean.

09 NIST validation

Measured against the corpus NIST publishes so forensic tools can be checked rather than trusted. Re-runnable, byte-exact, and reported per difficulty level because a single blended figure would hide the thing that matters.

What the first measurement found. The carver had only ever been tested on images this project generated, and it passed everything. Run against NIST CFReDS L4_Graphic.dd it reported 50 artefacts where 9 files exist, matched exactly one byte-for-byte, and flagged none as uncertain, while printing "every artifact had a located footer".

Two percent precision, stated with total confidence, in the one project whose thesis is that it does not overclaim.

Scoring rules, chosen to be strict

  • A hit is a byte-identical SHA-256 match against a NIST source file. Not "looks like a JPEG", not "opens in a viewer". The same bytes, or it does not count.
  • Precision = exact matches ÷ artefacts reported. Every false positive costs.
  • Recall = source files recovered ÷ source files contiguously present in that image. Dividing by the whole corpus marked the tool down for files that were never in the image, that was an error in the measurement, since corrected.
  • Where nothing is contiguous, recall is n/a, never 0%: there was no intact file to recover.
NIST levelpresentreported exactprecisionrecall what the level tests
L066 6100.0% 100.0% non-fragmented, the case signature carving is for
L166 6100.0% 100.0%sequential fragmentation
L203 00%n/a non-sequential fragmentation, nothing contiguous exists
L302 00%n/a missing fragments, nothing contiguous exists
L435 240.0%66.7% nested files

Throughput ~130 MB/s. Every L0 hit is HIGH confidence, meaning the extent came from the file's own structure rather than a footer search or a size cap.

What closed the gap: three formats had shortcut extent logic

Every miss traced to one cause, the carve began at exactly the right offset and ended at the wrong byte, so the digest never matched. The starts were never the problem; the ends were.

FormatThe shortcutThe real logic
TIFF"no end marker" → size cap, LOW confidence Walks every IFD, every external field value, and every strip and tile offset; the end is the furthest byte any of them reach
PCX"no end marker" → size cap, LOW confidence Decodes the run-length stream until it has produced the byte count the header declares, then accounts for the optional 769-byte VGA palette
GIFSearched for the 00 3B trailer pair , which occurs constantly inside LZW data Walks the block structure (extensions, image descriptors, sub-block chains) and arrives at the trailer instead of guessing at it
JPEGFirst FF D9 won, which belongs to the EXIF thumbnail, not the photograph Walks the segment structure, stepping over the APP1 payload whole, and scans for the end only after start-of-scan

PCX needed a second fix for precision. Its three-byte signature is far too short to stand alone, and because a run-length decoder eventually produces enough bytes from any input, the extent walk then "succeeded" on random data and reported the artefact at HIGH confidence. Enforcing the header invariants the specification actually requires, reserved byte zero, even bytesPerLine, width consistency, DPI range, zero filler, removed every remaining false positive.

Why there is no single headline number, and why that is the honest choice. L2 and L3 contain no contiguous file at all. Signature carving cannot reassemble non-contiguous extents, that is a property of the technique, not a defect in this implementation, and it is exactly why NIST built those images. Averaging L0 and L2 into one figure would erase the distinction an examiner depends on. The benchmark prints per level and refuses to emit a blend.

A tool that quotes one number across L0, L5 is telling you less than it knows.

It is automated, and it is a ratchet

scripts/benchmark_carver.py re-runs the whole matrix and writes evidence/carver_benchmark.json; tests/test_recovery_nist.py pins L0 at 100% precision, 100% recall, every hit HIGH confidence, all six formats detected. A change that drops any of those fails the suite. Both skip loudly when the corpus is absent, a test that passes because its data is missing is worse than no test.

11 The two ports, and what is actually behind them

The design has exactly two external dependencies, and both sit behind a port. That is why the implementation behind a port can change — and it has changed — without the attestation core moving. This section states what is behind each port today, at the honesty level rule 2 requires: what has actually run, not what was ordered.

SUPERSEDEDrecorded, not deleted

Earlier revisions of this document showed a Raspberry Pi Zero 2W co-signer and an ESP32 presence button, both labelled BUILT. Neither is the current design, and neither had run on hardware when it was labelled built. The Pi is gone — the co-signer is now a separate operating-system account. The ESP32 firmware still exists and its serial client is real code, not a stub, but no chain entry has ever been produced with a device attached, so it is labelled DESIGNED.

Why the old labels stay described — a document that quietly rewrites its own history is the failure mode this project exists to make impossible. Correcting a claim in public costs less than being caught holding it.
CO-SIGNERwhat it defends against

Separate OS account, selected. The witness key is generated inside a second Windows account and its directory is stripped of inherited permissions (icacls … /inheritance:r /grant:r witness:F). The operator account , the one that performs the erasure, cannot read it. Co-signing needs the second login.

Pi, and KVM guest, both dropped. The Pi bought physical separation at the price of a device that has to enumerate and join a network on stage; the KVM guest bought a separate admin domain but is reachable by anyone who owns the hypervisor, which on a laptop is the operator. Neither bought enough to pay for the failure mode it added.

Say precisely, an OS-account co-signer defends against the operator process, not against the machine’s administrator. An Administrators token reaches both accounts. The honest words are dual control, never physical separation. LB-03 is the test that keeps this sentence true rather than hopeful.
PRESENCEdesigned, not shipped

ESP32 button, designed and written, never run. It displays the pre-hash: the entry hashed with presence_ref empty, which is the only value that can exist before the human presses, because presence_ref is itself inside the signed preimage. The human confirms these bytes, and verify_presence_binding() re-derives them later.

WebAuthn authenticator, Phase 1, not implemented. A relying party binding the assertion to the exact pre-hash, on commodity hardware with no custom firmware. Cost: the key has no screen, so the human reads the value on the workstation rather than on the device that is attesting.

The claim to make today, presence is designed. No chain entry in this repository carries a presence_ref produced by a physical device (G19, G9), so the custody tier reached so far is SOFTWARE_KEY or WITNESS_COSIGNED, never FULL_CUSTODY.

What the hardware does not need

No GPU, at any point. Erasure is I/O-bound, carving is a byte scan, signing is microseconds, and the console is static HTML. Measured on this machine: a 500-entry chain verifies in 81 ms with both signature layers re-checked, of which only 3.9 ms is hashing, verification is signature-bound, not hash-bound , and a tamper is localised to the exact seq in 37 ms (evidence/chain_benchmark.json).

With the co-signer now an OS account, the virtualization requirement is gone: no VT-x, no hypervisor, no second physical device. What replaces it is a link. The two machines must reach each other, and that is now the single point of failure for the second signature, so it is tested in advance, on the exact transport used on the day (scripts/prep/g24_link_check.py).

Tested on the real machines (1 Sept), and it settled the transport. A USB-C to USB-C direct cable does NOT link two laptops, USB is host-to-device, so neither laptop will act as a device to the other, and this laptop has no Thunderbolt/USB4 controller to carry the one exception. No USB-Ethernet adapter was present either (scripts/prep/link_detect.ps1 → evidence/link_detect.json). Both machines do have Wi-Fi, so the chosen transport is a Wi-Fi hotspot, a phone's, or this laptop's own Mobile Hotspot, with both laptops on one subnet (scripts/prep/wifi_link.md). Wireless carries the handshake only; it is trusted with nothing. A hostile network can drop packets, in which case the operation fails closed and writes a REFUSED entry, it cannot forge a signature it has no key for. The one risk is AP client-isolation on venue Wi-Fi, which is why a hotspot the team controls is preferred and why the link is rehearsed rather than assumed.

12 Standards mapping

Two standards, one document. The mapping lives in code as CLAUSE_MAP, so "every field maps to a named clause" is an executable test rather than a review opinion.

NIST SP 800-88 Rev. 2Appendix G

Certificate of Sanitization. Media block, method type actually achieved, method details, tool and version, verification method, post-sanitization classification, and both signature blocks.

The honest part: method type is the weakest method across every covered erase. One Purge cannot launder a Clear performed on another device in the same case.

BSA 2023Section 63(4)

Since 2023 the certificate must be signed by both the person in charge of the device and an expert, Schedule Part A and Part B.

This is why the tool dual-signs. A single-signature tool cannot produce a §63(4)-shaped certificate at all. The statute asks for two parties, so the ledger asks for two keys.

The four conditions of §63(2), and what answers each

ClauseWhat it requiresAnswered by
63(2)(a)Regular use by a person with lawful control declaration operator's statement
63(2)(b)Information regularly fed in the ordinary course declaration operator's statement
63(2)(c)The device operated properly throughout mechanism chain verification, every entry re-hashes, links, and carries a valid signature
63(2)(d)Content derived from information fed in mechanism result_hash, the entry commits to the operation's own record

Two of the four are answered by a mechanism and two by a human declaration, and the certificate labels which is which. Presenting all four as machine-proven would be the exact overclaim this project exists to avoid.

13 Three attacks, three layers

Each attack defeats the layer above it. The third is the one no single-machine ledger can answer, and it is the demo.

A fourth attack sits outside all three: doctoring the stored result record while leaving the entry's signature untouched. The chain still verifies, the signature covers the hash, and the hash is unchanged. Only re-checking every stored record against its committed digest catches it, which cli verify now does, exiting 1.

14 The case, the signer, and the tool itself

Chaining answers one question completely: was this device’s history altered after it was written. Three questions sit just outside it, and each was answerable only by trusting somebody. Each is now a signed fact instead.

What these four have in common. Every one closes an omission rather than an alteration — a thing that could be missing without anything breaking. A chain notices what changed inside it. It is structurally blind to what was never in it, to what stopped being in it one level up, and to who or what put it there. Alteration was already solved; these are the remaining silences.

14.1 A whole device disappears from a case

A chain covers one device. A seizure does not: a laptop, two phones, four sticks, a NAS — each examined separately, each with its own chain, correctly so. Merging them into one ledger would force a global ordering on operations that genuinely happened in parallel, and would make one device’s verification depend on another’s.

That leaves the hole exactly one level up. Delete usb_03.json from the evidence folder and every surviving chain still verifies perfectly, because nothing inside a chain knows how many siblings it had. It is the same omission attack the project exists to close, moved up one level of aggregation — and it is closed the same way: bind the set, then put the binding somewhere the operator cannot rewrite.

CASE ROOTsrc/attestation/case.py

A Merkle root over every device’s head, sorted by device_id so two examiners with the same evidence compute the same root. Order-dependence would make it useless for the one comparison it exists to support.

Each leaf commits to device_id, chain_id, head_hash and count, length-prefixed. The count is there for the same reason the witness publishes its own: a head hash alone cannot tell a chain that legitimately ended at seq 4 from one truncated to seq 4.

Selective disclosure comes free — device_proof() shows one drive belongs to the case in O(log n) sibling hashes without revealing the others’ contents or even their identifiers. The real need: one drive released to its owner while the rest of the case stays live.
HONESTYwhat it refuses to say

A device added after the root was fixed is reported but explicitly not called tampering. A drive examined on day three looks identical to an inserted one, and crying wolf on the most ordinary event in a live case would be its own kind of dishonesty.

An empty case raises rather than returning a zero root. A zero root verifies against nothing while looking like a commitment.

The manifest states in its own text that it is a claim the operator made about their own case until it is anchored or co-signed. Same rule that makes a chain head evidence rather than an assertion.

14.2 The signing key is swapped for someone else’s

operator_key_id was already inside the preimage, so every entry stated which key signed it. Nothing stated which key was supposed to. A chain whose entry 7 is signed by a key nobody recognises verifies perfectly — each signature is checked against whatever key the verifier was handed, and a verifier handed the attacker’s key confirms the attacker’s signature with complete honesty.

Keys change for ordinary reasons: an examiner leaves, a laptop is reimaged, a token is lost. None of those should be indistinguishable from a substitution.

The rule: a signer may change; a signer may not change silently.

A rotation is announced by a SIGNER_CHANGE entry signed by the outgoing key, naming the incoming one. That ordering is the entire design: the outgoing key is the only party that can still prove it was the legitimate holder, so it is the only party whose word about its own succession means anything. An incoming key announcing itself is precisely what an attacker with a fresh keypair would do, and is rejected — as is a retrospective announcement, because paperwork arriving after the new key already signed is a note, not an authorisation.

CHANGE_REASONS is a closed vocabulary and it includes COMPROMISE on purpose. Free text would let a compromise be filed as a routine handover; a vocabulary lacking the word nobody wants to write guarantees it gets written as ROTATION. LOSS is recorded as weaker than a rotation rather than equivalent — it cannot be signed by the key it replaces — and the record says so itself.

Stated in the module, not discovered later. This cannot detect a compromise that happened before the first entry, and it cannot stop an attacker holding the current private key from signing a valid handover. Narrowing the attack to “you must compromise the current key and use it” is the honest claim. “Revocation prevents compromise” is not, and nothing here says it.

14.3 Which build produced this?

Every entry said what was done. None said what did it. That left the first question asked of any automated forensic result unanswerable from the record itself: which build produced this, and is it the build that was validated? “The tool” stops being an answer the moment the code changes — which it does, between validation and the case, between the first drive and the fortieth.

tool_ref is now the 16th signed field (ENTRY_VERSION 3): a version plus a SHA-256 over the fourteen modules whose source can change what an entry says. Inside the preimage, not beside it, for the same reason outcome had to move there — a field describing the operation that lives outside the signature can be edited afterwards to make one build’s output look like another’s.

DESIGNdetails that matter

Line endings are normalised before hashing. Git rewrites them on checkout, so a raw byte digest would report a different tool for identical code — a false alarm exactly where cross-platform verification matters most.

A missing module hashes as absent rather than being skipped, so deleting a module is detectable. Otherwise removal would be the one code change the tool could not see in itself.

Chain.append takes no tool_ref parameter. A value supplied by the operator would be a claim about the tool made by the party the tool exists to constrain.

A mismatch reports, never fails. Chains outlive builds; an entry from last month’s version is normal, and this field exists to make it visible rather than to forbid it.
NOT SELF-MODIFYINGthe boundary

This is not a self-improving tool, and the distinction is not cosmetic. A process that rewrites itself is a process the certificate cannot describe — and BSA 2023 s.63(4) requires the certificate to describe the process. Self-modification is inadmissible, not merely risky.

What self-attestation enables is the honest version: the tool may change between versions, and every entry states which side of every change it falls on. Evolution becomes a signed, dated fact in the same ledger as the evidence, instead of an unrecorded event nobody can bound.

A test asserts no attested module writes to its own source. The boundary is enforced, not just intended.

14.4 The tool gets harder to break with every real task

Fixtures are chosen by their author, so they encode what the author already thought of. Real drives are chosen by nobody — a truncated JPEG at an awkward offset, an erase that hit three bad sectors, a chain written under a different locale. Those are the inputs that find bugs, and until now they were seen once and discarded.

Every real run is pinned as a case the tool must keep reproducing. A pinned case is a digest plus enough context to recompute it, never the evidence: the corpus is committed to a public repository, so it holds no drive contents, no case identifiers and no machine identity. Inputs are matched by content rather than path, so a case pinned on one laptop replays on another.

Two failure modes it is built to avoid, because both would make the corpus worse than not having one.

Reporting green while testing nothing. An input that is not present on this machine is UNAVAILABLE, which is deliberately not a pass. A malformed case file is BROKEN, not skipped — silently ignoring entries would let the suite shrink to zero unnoticed.

Treating drift as a verdict. If a run was wrong, pinning it pinned the bug. A mismatch is therefore “which of these two is right?” and never an automatic finding against the newer code. Both builds are named in the report — which is what tool_ref is for.

15 Fragment reassembly

Signature carving finds a header, reads forward, stops at a footer. That works only while the file is contiguous — and on the benchmark NIST built to test exactly this, it recovers nothing at all.

The zero this removes was structural, not a tuning problem. NIST CFReDS levels 2 and 3 contain no contiguous file. A scanner that reads forward cannot recover a file whose second half is stored before its first, so every signature carver scores 0% on them — PhotoRec, Scalpel, Foremost, and this project’s own carver until now.

000_0021.png is now recovered from CFReDS L2 byte-identically: 12,966,639 bytes, SHA-256 9779c1ee…, decoding as PNG 2580×1932 RGB.

15.1 Why this is not the usual guesswork

Reassembly is normally heuristic: try gap sizes, see whether a decoder complains, keep whichever result looks least broken. That produces files nobody should put in evidence, because “the decoder did not object” is not a statement about the original bytes. A JPEG missing its middle third still opens.

This uses formats that carry their own integrity checks, so every fragment is proven to belong before it is used:

StepWhat decides itWhy it cannot be a guess
Which bytes are chunksCRC-32 over each chunk’s own type+data A wrong fragment fails its own checksum. 1,583 chunks found this way; 4 MB of SHA-256 output yields none.
Which chunks form a fragmentphysical adjacency in the image Chunks that abut were laid down together. This turns 1,583 chunks into 2 runs — an intractable ordering problem into a solved one.
Which fragment comes firstthe PNG format itself IHDR must open a file and IEND must close it. The run holding IHDR is the first fragment. Nothing is preferred.
The chunk split across the cutexhaustive split search, CRC-32 as oracle Its head ends fragment one and its tail begins fragment two, so it CRCs in neither place. Every split is tried; a wrong one is rejected.
Whether the result is coherenta real decoder, run last Confirms the assembly parses. Deliberately not the deciding check.

15.2 The boundary chunk is the whole difficulty

Without it the rebuild is 8,204 bytes short — and it still decodes perfectly. That is precisely the failure a decoder check cannot catch, and precisely why byte-identity against ground truth is the only acceptable bar here. A reassembled file that merely opens is worthless as evidence.

A bug in this module, kept because it is instructive. The straddle search found the boundary chunk in the prototype and lost it in the module. The first fragment ends 1,730 bytes before the end of the image and the chunk’s head is exactly those 1,730 bytes — which range(8, 1730) excludes. It failed as “no boundary chunk” rather than as an error, so the run still looked successful and produced a file that decoded. Only the hash comparison caught it.

15.3 What is claimed

Every result is labelled reassembled=True with its fragment list, so it is never presented as a contiguous find. Contiguous files are deliberately not reported by this module, so they cannot be double-counted in any recall figure. The test suite carries the control that matters: the plain carver still recovers nothing from L2, so this cannot be the ordinary carver working while the reassembler takes the credit.

17 The certificate: what it must say, and who must say it

Read from NIST SP 800-88 Rev. 2 and the BSA 2023 Schedule themselves rather than from summaries of them. Both turned out to require things the tool was not recording.

17.1 NIST’s own certificate already has a second signer

Appendix C, Fig. 2 of Rev. 2 — the sample Certificate of Sanitization — has TWO signature blocks. The second is labelled Concurrence.

This inverts the burden of the whole design. The second signature stops being something to justify and becomes something to implement. Every other tool prints that block as an empty line for someone to sign by hand later, or omits it. Akhanda makes it a cryptographic signature from a key on a machine the operator cannot write to.

India’s evidence law arrives at the same shape independently. BSA 2023 §63(4) requires two certificates: Part A from the party holding the device, Part B from an expert. Two standards, written on different continents for different purposes, both requiring two people — and the chain’s operator_sig / concur_sig pair is the intersection.

17.2 Verification is not validation, and only one was implemented

Rev. 2 introduces sanitization assurance as two distinct things, and the Appendix C form carries a Verification/Status: field and a separate Validation: field:

Rev. 2 conceptWhat it isAkhanda
Verification §4.5.1 “inspecting the outcomes of a sanitization technique to determine the outcome of the technique used” — completion status, errors, anomalies, media health read_back_sample · bad_ranges · aborted · outcome
implemented, and exceeds the guideline
Validation §4.5.2 “a decision to either approve the sanitization as being effective or reject it, which would require repeating the sanitization method using a different sanitization technique or escalating to a more secure sanitization method” attestation/validation.py
added; previously absent

THE TOOL MUST NOT DECIDE, and that is the design rather than a limitation. §4.5.2 weighs “the sanitization outcomes and the sensitivity of the target data”, turning on whether “the organization accepts any residual risks”. Software knows the outcomes and nothing else.

A tool that auto-approves has not implemented validation — it has renamed verification and buried a human judgement inside a boolean. A perfect run with zero skipped regions is still AWAITING_DECISION.

All five considerations §4.5.2 lists are assessed, and what software cannot determine is reported undetermined rather than clear — treating “we cannot tell” as “no problem” is how a rejection ground quietly disappears:

GroundDetermined how
G1, regions no longer accessible through the interface measured, from bad_ranges and aborted
G5, scope too narrow (overprovisioning) measured, clearing flash is the standard’s own example, so this triggers on the normal case
G2, method inappropriate for the security category undetermined, needs the data’s sensitivity
G3, unqualified personnel, uncalibrated tools undetermined, tool_ref identifies the build and the signing key. Identifying is not qualifying.
G4, outcome below the organisation’s minimum undetermined, a policy threshold this tool does not hold

decide() refuses a decision with no named validator, no rationale, or no stated data sensitivity — and refuses a rejection with no remedy, because §4.5.2 says rejection requires repeating or escalating, so a rejection naming neither is a complaint rather than a decision. Approving over a triggered ground is permitted and recorded as such, so the certificate shows the risk was accepted rather than absent.

17.3 A device path is not an identity

Three independent authorities require the same block of fields, and the tool was recording none of them — it recorded a path.

REQUIRED BYthree sources, same fields

NIST Rev. 2, Appendix C, Vendor/Make · Media Type · Model Number · Serial Number · Property Number · Source · Classification · Operational/Damaged

BSA §63(4) Part A, Make & Model · Colour · Serial Number · IMEI/UIN/UID/MAC/Cloud ID

Blancco’s own certificate, Manufacturer · Chassis type · Model · Colour · Serial numbers

/dev/sdb is whichever drive was plugged in second; \\.\PhysicalDrive2 is whichever one Windows enumerated third. Neither survives a reboot, and neither finds a drive in an evidence bag six months later.
UNAVAILABLE ≠ BLANKthe whole design

On a certificate an empty serial field and an unread serial field look identical — and a reader will conclude the drive has no serial rather than that nobody looked.

Every field is either a value with its source named (which sysfs path, which IOCTL) or an explicit unavailable with a reason. A file image reports that it has no physical identity, which is a different fact from a read that failed.

Fields no software can determine, Property Number, Source, Classification, Colour, say requires human entry rather than being invented or silently omitted.

is_identified() turns on the serial alone. Make and model identify a product, and a lab may hold forty of the same product; only the serial identifies the item on the bench.

Where it is signed, and why not a 17th field. Device identity and the validation record ride in the result record, which result_hash already covers — and result_hash is inside the signed preimage, with the stored result re-verified against it. So both are tamper-evident without an ENTRY_VERSION 4 bump and a synchronised change across three verifier implementations, to gain a property the result record already provides. A test asserts that stripping device_identity moves the digest.

18 Outliving the algorithm that signed it

A chain of custody is read when the case is heard, not when it is written. That gap is measured in years, and cryptography has a shelf life.

Dates, not adjectives.

NIST FIPS 203 / 204 / 205 finalised13 August 2024
RSA-2048 and ECC P-256 deprecated2030
Federal deadline for digital signatures2031
Quantum-vulnerable algorithms removed from NIST standards2035
Indian criminal proceedings, trial through appeal10–20 years

Ed25519 is an elliptic-curve signature. A chain signed in 2026 may be examined in 2040 — five years after the algorithm that signed it left the standards. The literature names this exactly: ACPO, NIST SP 800-101 and ISO/IEC 27037 “make no provision for algorithm agility or quantum resilience”, and evidence authenticated under a broken scheme becomes “legally contestable”.

Every entry now carries an ML-DSA-65 signature (NIST FIPS 204, security category 3) alongside the Ed25519 one, over the same entry hash.

18.1 Why this is additive, and why that is the whole point

operator_sig and concur_sig are attached after signing — they are signatures over the entry hash, not fields inside the preimage. A post-quantum signature is the same shape, so it costs nothing structural:

What a 17th hashed field would have costWhat this cost instead
ENTRY_VERSION 3 → 4unchanged at 3
16 hashed fields → 17unchanged at 16
Every existing entry hash invalidatedhashes unchanged
Synchronised change across Python, JavaScript and Rustnone, all three read a PQ-signed chain untouched

The three-implementation canary passes without modification, which is the test that proves the claim rather than the claim itself.

18.2 Stripping is the attack, and the classical verifier cannot see it

An adversary who cannot forge either signature can still DELETE the post-quantum one, silently downgrading the chain to the algorithm they expect to break — and the ordinary verifier stays perfectly happy, because nothing it checks has changed. That is precisely why the post-quantum layer needs its own detection.

pq_algorithm is recorded separately from the signature itself. An entry that names an algorithm and carries no signature for it is STRIPPED — a finding, not an absence. The mirror attack, deleting the label instead of the signature so nothing can be checked against a key, is caught the same way.

18.3 Four states that must never collapse into two

StateWhat it means
NOT_PROTECTEDNo PQ layer. Normal for a chain written before the migration — not a defect.
STRIPPEDAn algorithm is named and the signature is gone. An attack.
PROTECTEDVerified against a supplied public key.
SIGNATURE_INVALIDIt did not verify.

And when no public key is supplied, the result is unverified — never valid. A migration is a mixture by nature, so a chain that is two of three protected reports exactly that rather than rounding to whichever end flatters it.

COSTmeasured on this machine

Ed25519 — 64 B signature, verify 0.099 ms

A 500-entry chain verifies in 91 ms instead of 81 ms. The file grows from ~33 KB to ~1.7 MB, beside the multi-gigabyte images it describes.

The price of a signature that lasts is a bigger file and ten milliseconds.
THE CLAIMand what it is not

Claimed: that this chain carries a signature made with an algorithm NIST expects to still accept in 2040, alongside the classical one.

Not claimed: that quantum computers will break Ed25519 by any particular date — unknowable, and unnecessary to the argument. Nor that post-quantum chain-of-custody is our idea: the literature already recommends it. First implementer, not first thinker.

The argument rests on standards deprecation and legal contestability, both dated and citable. Reaching for the stronger version makes it weaker.

19 Platform reach, and the driver question

How far userspace actually gets on each operating system, what sits beyond it, and why the thing beyond it is not being shipped.

19.1 No kernel driver. Stated plainly, because the answer is no.

AKHANDA ships no kernel driver and will not ask you to install one. Not as a limitation reluctantly admitted — as a decision, with reasons that survive being asked about.

It could not be shipped in time even if it were wanted. A Windows kernel driver must be signed through the Microsoft Hardware Developer Program: an EV code-signing certificate, a partner account, hardware-lab attestation, and weeks of turnaround. Nothing in that sequence fits a prep window measured in days.

The unsigned alternative is worse than the gap. Loading an unsigned driver means disabling Secure Boot or enabling test-signing on the examiner’s machine — weakening the integrity of the very workstation whose output is meant to be evidence. A tool that asks a forensic examiner to turn off Secure Boot has damaged the case it was brought in to support.

And it is not needed for what the problem statement asks. Raw whole-disk access — \\.\PhysicalDriveN on Windows, /dev/sdX on Linux — is available to an elevated userspace process on every supported platform. Every module below reaches its media without one.

What a driver would buy is narrow and specific, and it is already in the disclosed limits rather than hidden: reaching data resident inside filesystem metadata — a small file stored in its own NTFS MFT record, an ext4 inode table, a journal. That data lives in no data run, so no userspace write addresses it. The certificate says so; a driver would change that sentence and nothing else on this page.

Purge is a Linux capability and is recorded as one. On Windows and macOS there is no userspace path to ATA Secure Erase or NVMe Sanitize, so the tool achieves Clear and writes Clear. Asking for Purge there does not produce a Purge record — it produces a Clear record with the reason attached.

19.2 Alternate data streams: a verified erasure that left the data behind

SIH26149 requires the file eraser to remove “associated metadata and residual traces”. A named NTFS stream is precisely that, and it is the trace that survived everything the eraser did.

A named stream shares a file’s directory entry but not its bytes. The pattern write, the read-back, the verification, the name scrub, the truncate, the unlink — all of it addressed the default stream. So the tool could report VERIFIED while a payload sat intact in file.txt:hidden. Every check passed. Every check was looking at the wrong stream.

ORDERoverwrite, then delete

Streams are erased before the file is unlinked. Unlinking first would drop them along with the file, leaving their blocks unreferenced but never overwritten — ordinary deletion wearing the name of erasure. Same reasoning as the main eraser’s own ordering.

A stream that could not be erased downgrades the outcome to PARTIAL: it is a surviving copy of data the function has just reported destroyed, so it cannot be VERIFIED whatever the main stream did.
HONESTYfound ≠ erased ≠ absent

found is recorded separately from erased, and the report is present even when the count is zero. “This file had none” and “streams were never looked for” are different facts; only the first is a statement about the file.

On ext4 or APFS the report says not applicable rather than returning a clean zero that would imply a check ran and passed.

Clear level only. A stream small enough to be resident in the MFT record is unreachable from userspace, exactly as the file’s own resident data is.

19.3 The write guard, and the hole that was in it

The blocklist named /dev/sda, /dev/nvme0n1 and C:\ — and did not name \\.\PhysicalDrive0, which on the development machine is the system disk. A confirm token plus one environment variable would have reached it. Nobody wrote that path down, so nothing protected it.

A hand-written blocklist protects only the paths someone thought of. Two of the six gates below deliberately do not depend on anyone’s imagination.

#GateWhat it stops
1confirm tokena stray argument becoming a wipe
2AKHANDA_ALLOW_DEVICE_WRITE=1an independent second switch
3REFUSED_PREFIXESthe named patterns — necessary, not sufficient
4protected roots (Windows)the volume holding the OS or this repository
5/proc/mountsthe device actually mounted at /, /boot, /home
6AKHANDA_TARGET_DEVICEmust equal the target exactly, for any whole disk

Gate 6 is what makes a typo harmless. A boolean flag plus a mistyped drive number is a wiped system disk — and the flag would have been telling the truth the whole time. Naming the exact device means a typo reaches nothing. It authorises; it can never override the blocklist, so naming PhysicalDrive0 exactly is still refused.

Gate 5 asks the system rather than the name. On a forensic workstation the evidence drive may well be /dev/sda. A name-based blocklist cannot tell that apart from a boot disk; /proc/mounts can, so the evidence drive is permitted while the running system never is.

Three bugs were introduced while writing this guard, all the same shape — normalising POSIX paths for Windows matching. The worst refused every target on Linux, including the USB stick the guard exists to permit, because every absolute POSIX path shares the anchor /. A guard that blocks everything is as broken as one that blocks nothing, and it would have surfaced on Linux, at the demo, with a drive plugged in. The tests assert both halves: the system disk is refused, and the evidence drive is permitted.

19.4 Testing filesystems without touching a disk

detect_filesystem() is claimed to work across filesystems, and had only ever run against the one NTFS volume this repository lives on — a claim covering four cases written from one. scripts/prep/fs_matrix.ps1 runs it against real NTFS, FAT32, exFAT and ReFS volumes, every one backed by a .vhdx file. No physical disk is enumerated, selected, formatted or written to, and diskpart is driven with an explicit select vdisk file= rather than a disk number — there is no disk-number arithmetic that could land somewhere else.

It matters more than it looks. A detector returning unknown does not crash: it downgrades the recorded outcome to UNVERIFIED. And ReFS is copy-on-write, so it must produce PARTIAL even when the read-back matched, because the read came back through the same layer that may have written the new bytes elsewhere.

21 Automation, and the rules it enforces on itself

One runner, eleven checks, and three rules that exist because each was broken here first.

scripts/run_all.py runs every check this project has and writes both evidence/run_all.log and evidence/run_all.json on every run. .github/workflows/checks.yml drives the same runner rather than listing its own checks, so CI cannot drift into a second, quietly different suite.

RULE 1no early exit

A runner that stops at the first failure tells you about one problem and hides the rest — so the next run finds the second, and the run after that finds the third. Every check runs to completion regardless of what failed before it; the exit code is decided at the end from the whole picture.

RULE 2failures recorded more fully than passes

A pass needs a name, a duration and an exit code. A failure gets its entire stdout and stderr, untruncated, with the command and working directory — because that is the only record of why, and a log that truncates the one line you need is a log nobody trusts twice.

RULE 3 — skipped is not passed, and neither is not-run. A missing toolchain reports SKIPPED with the reason. “cargo is not on PATH” and “the Rust tests passed” must never look the same, and a suite that quietly shrinks when a tool goes missing reports green while testing less.

This rule was broken in the runner that enforces it. A --quick run printed skipped 0 while three checks were never executed — the header said “8 of 11” but the summary read clean, so a glance would take a partial run for a complete one. Deselected checks are now on the summary line, named, and the verdict reads GREEN (PARTIAL — 3 check(s) not run).

The unspoken risk. Reference implementations exist for every role so nobody is blocked on an empty file and the demo cannot fail because one person ran out of time. But ownership still sits with the named role, they extend it, test it on real media, and must be able to explain it. A teammate who only runs code they did not reason through cannot answer for it under split Q&A, and that is exactly where hackathon projects lose marks.

Known gaps, ranked

  • No co-signer or presence device has ever run, the witness node and the presence handshake have never been exercised against physical hardware. Every claim about them is a configuration, not a result. This outranks everything below it.
  • Drive erasure has never touched real removable media, the file path is verified on real NTFS, but no USB stick has been wiped. The NIST decision tree for flash is reasoned, not observed.
  • The presence device is shown the wrong hash, it displays a prefix of the result digest, not the entry hash that gets signed, and the module docstring claims the opposite. Needs a two-phase design, because the entry hash depends on the presence reference. A wrong comment is a lie a judge can read.
  • Recovery confidence scoring, a heuristic (header/footer completeness, entropy) is the right call at this scale. A trained classifier is scope that is not needed, and would be the only reason to want a GPU.
  • Keys are readable files on disk, AKHANDA_KEY_PASSPHRASE encrypts the operator key at rest; the witness key is not yet passphrase-derived. Deferred and disclosed rather than silently carried.

Three bugs real hardware found that no test could

Kept on this page because they are the argument for testing on the machine you will present from, not only in CI.

24 What it cannot do

Stated first, never trimmed. A reviewer who finds a gap themselves discounts everything else in the document.

LIMIT 01integrity, not completeness

The chain proves nothing was altered after being written. It cannot prove nothing was withheld. An operator who logs nine of ten operations passes every check in this repository. Recording refusals narrows this , a blocked attempt now leaves a trace, but an operation never attempted through the tool leaves none, and no single-operator ledger can close that.

LIMIT 02tail truncation

Dropping the most recent entries leaves a shorter, self-consistent chain that local verification cannot distinguish from a chain that was always that length. Only the witness's independent head record separates the two. There is a test that asserts this limit still exists, so it cannot be quietly claimed as solved.

LIMIT 03presence ≠ key protection

The ESP32 is not a secure element. CVE-2019-17391 extracts ESP32 eFuse keys by voltage glitching and is unpatchable on shipped silicon. The device confirms a human was physically present. It does not hold, protect, or attest a key, and no output ever says otherwise.

LIMIT 04anchoring is cryptographic, not legal

OpenTimestamps is not legally recognised in Indian courts. It provides a cryptographic guarantee of the same class courts increasingly accept. That is the claim, and nothing stronger appears anywhere in the tool's output.

LIMIT 05flash cannot reach Purge

USB flash and SD cards support neither ATA Secure Erase nor NVMe Sanitize, and their translation layers retain spare blocks the host cannot address. On this media the tool achieves Clear and records Clear, even when Purge was explicitly requested, in which case it also records why.

LIMIT 06carving is not recovery

Fragmented files carve as garbage after the first fragment, and nothing in the byte stream announces it. Original filenames are gone with the directory entries, the names in the output were invented from byte offsets. A missing footer means the end boundary is a capped guess, flagged as truncated.

LIMIT 07form, not admissibility

Every certificate field maps to a named clause of NIST SP 800-88 Rev. 2 or the Bharatiya Sakshya Adhiniyam 2023. That is a statement about the form of the document. Whether a record is admitted is a matter for the court, never for the tool.
